# Daily Content Pipeline

This runbook captures the default cross-platform workflow.

## Strategy

- Do not drive Xiaohongshu with a flat keyword list. Keywords get repetitive quickly and only describe surface topics.
- Generate one `contentIntent` per day: audience, situation, tension, point of view, optional practice, and words to avoid.
- Use `creator-systems` as the thinking layer: attention, goals, writing, self-design, systems.
- Use `realist-perspective` as the X/Rednote voice layer: short Chinese judgment, reality, boundaries, sleep, body, cash flow, and less performative advice.
- Use the account surface strategy for platform fit: 成年人清醒生活 + 内容创作者的自我管理.
- X can be sharper and shorter. Xiaohongshu should read like a life note with title, body, tags, and one cover line.
- Avoid making Xiaohongshu look like an AI/tools/product account unless the user explicitly changes the strategy.

## Default Command

Generate and enqueue today's batch:

```bash
XPOST_LIAOBOTS_AUTHCODE="..." node bin/xpost.js daily-plan --count 5 --rednote-count 2 --x-window-start 10:00 --x-window-end 23:00 --rednote-window-start 11:00 --rednote-window-end 21:30 --json
```

Preview today's batch without writing `queue.json`, `rednote-queue.json`, or archive state:

```bash
XPOST_LIAOBOTS_AUTHCODE="..." node bin/xpost.js daily-plan --dry-run --count 2 --rednote-count 1 --json
```

The command:

1. Reads the creator systems thinking skill and the realist voice skill.
2. Builds one `contentIntent`.
3. Generates 5 X posts from that same intent.
4. Scores the X posts for Xiaohongshu fit.
5. Rewrites the best 2 posts into Xiaohongshu notes.
6. Enqueues X items in `queue.json` and Rednote items in `rednote-queue.json`.

It does not publish by itself. With `--dry-run`, it also does not enqueue.

After a worker publishes a queued item, it upserts the content into `content-archive.json`. The archive keeps published content separate from queue execution state, and preserves `contentIntent` for items generated by `daily-plan`.

## Daily Automation

The recommended background setup is one planner, two workers, and one daily metrics capture job:

```bash
node bin/xpost.js service install --kind daily-agent --yes --schedule daily-random --count 5 --rednote-count 2 --x-window-start 10:00 --x-window-end 23:00 --rednote-window-start 11:00 --rednote-window-end 21:30 --auth-code "..."
node bin/xpost.js service start --kind daily-agent

node bin/xpost.js service install --yes --interval 180 --account _example_
node bin/xpost.js service start

node bin/xpost.js service install --kind rednote --yes --interval 300 --publish --image-provider liao --auth-code "..."
node bin/xpost.js service start --kind rednote

node bin/xpost.js service install --kind metrics --yes --metrics-time 09:30 --metrics-days 2 --source daily-plan
node bin/xpost.js service start --kind metrics
```

`daily-agent` runs at local 00:00 and does not kickstart on service start unless `--kickstart` is passed. This prevents accidental duplicate generation when restarting services.
`metrics` runs once daily at local 09:30 and captures recent `daily-plan` X engagement metrics after posts have had time to collect impressions.
Replace `_example_` with the expected X handle, or omit `--account` only for a local test runner where account locking is not needed.

## Duplicate Guard

Daily batches are tagged:

```json
{
  "source": "daily-plan",
  "planDate": "2026-05-30"
}
```

If either the X queue or Rednote queue already contains a non-failed item with the same `source` and `planDate`, `daily-plan` skips the day. Failed items can be retried explicitly with `xpost retry` or `xpost rednote-retry`.

## Inspecting Results

```bash
node bin/xpost.js list --json
node bin/xpost.js rednote-list --json
node bin/xpost.js archive-list --since 2026-05-30 --json
node bin/xpost.js archive-report --since 2026-05-30 --json
node bin/xpost.js metrics-capture --since 2026-05-30 --source daily-plan --json
tail -n 80 ~/.xpost-agent/logs/daily-agent.out.log
tail -n 80 ~/.xpost-agent/logs/daily-agent.err.log
```

For real posting checks, keep using the worker-specific runbooks. Browser Relay controls Chrome, so success is only real after queue state and screenshots show the expected posted/drafted state.

After a post has collected impressions, run `metrics-capture` to append X views, replies, reposts, likes, bookmarks, and engagement rate to the archive. `weekly-review` uses those local snapshots as content-quality evidence for future prompt tuning.
